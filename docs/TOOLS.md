# Tool catalogue (v1 contract)

Conventions: every tool name is `dockhand_<verb>_<resource>`. `env` = `environment_id: int` (optional when a default is configured). `ref` = container ID (12–64 hex) **or** exact name; resolved server-side. Column **Async** uses the patterns in `docs/ARCHITECTURE.md` §4. **Perm** = DockHand Enterprise RBAC permission the underlying endpoint requires (from the spec; `—` = not stated in spec, verify at implementation).

Annotations: `read` tools → `readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: true`. `operator` → `readOnlyHint: false, destructiveHint: false`. `destructive` → `destructiveHint: true`. All set `openWorldHint: true` (we talk to an external system), except `dockhand_get_operation`, which only reads this server's in-process registry (`openWorldHint: false`).

Common optional inputs on every write tool: `wait: bool = true`, `timeout_seconds: int = 60 (1..300)`. Destructive tools add `confirm: bool = false`, which is only honoured on the confirm path of `DOCKHAND_MCP_CONFIRM_MODE` (D-006: `param`, or `auto` when the request does not declare form elicitation); with elicitation the human approves through the client and `confirm` is ignored.

Every tool also declares a `title` and an `outputSchema` (the envelope from `docs/ARCHITECTURE.md` §6, with `data` specialised where cheap).

## Read tier (profile ≥ read-only) — Phase 2

Every row is implemented (`dockhand_health` and `dockhand_get_operation` in S1, `dockhand_list_tags` for #3, the other 48 in S2) except `dockhand_list_notifications`; S3a added `lint` to `dockhand_get_stack_compose` and guardrail findings to `dockhand_validate_stack_compose`. **Status**: `done` = implemented against the spec's 200 schema; `experimental` = implemented, but the spec has no 200 schema (or its schema disagrees with live DockHand), so the shape was inferred and checked against a live DockHand 1.0.46 (read-only) — the note says what was seen. **Perm** was checked against the spec text of every endpoint the tool calls; `—` = the spec states no permission.

Read-tier conventions (S2):
- `env` is `environment_id`, always optional in the schema. Resolution order: the argument; else `DOCKHAND_DEFAULT_ENVIRONMENT_ID`; else, if DockHand has exactly one environment, that one (reported in `warnings`); else `validation_error` listing every environment's id and name. Every environment-scoped tool therefore also declares `GET /api/environments`. Tools marked `env?` treat it as an optional filter instead (all environments when omitted) and never default it.
- Each call sends the environment under the exact name its route takes: `env` for most, `environmentId` (`/api/activity`, `/api/audit`, `/api/schedules/executions`), `environment_id` (`/api/activity/stats`).
- Lists return `{items, count, total?, has_more}` (`limit`/`offset` where shown). Long texts (logs) keep the newest part and report `truncated`, `bytes`, `dropped_bytes`.
- Every result's `data` passes a key-based secret redaction (`guardrails/secrets.py`): a non-null, non-boolean value under a sensitive key name (e.g. `webhookSecret`, `password`, `token`, `apiKey`, anything ending in `Secret`/`Token`/`Password`) becomes `"<redacted>"`; the key stays. Then DockHand's free text (values under `message`, `error`, `status`, `output`, `reason`, `detail`, `warning`, `hint` keys and their suffixes, e.g. `State.Error`, a health check's `Output`, a container's `status`) passes the string layers of the operation-output redaction, without stack values (S3e; docs/SECURITY.md "Output redaction"). Content the tool exists to return (logs, compose, `.env`, stack variables, `Config.Env` under `redact_env`) is not free text and is unchanged.

## Operator tier (profile ≥ operator) — Phase 3a

Implemented in S3a: 36 tools. The optional `dockhand_adopt_stacks` / `dockhand_scan_for_stacks` (scan walks a DockHand-host filesystem path) and `dockhand_test_notification` (notifications were skipped in S2) are not implemented. **Status** as in the read tier; "live" means exercised against a live DockHand 1.0.46 in the test environment during S3a's write checks. **Perm** is the spec's text for every endpoint the tool calls (`—` = none stated).

Operator-tier conventions (S3a):
- Every tool takes `wait` (default `true`) and `timeout_seconds` (1..300; the server's `DOCKHAND_MCP_DEFAULT_TIMEOUT` when omitted, capped at `DOCKHAND_MCP_MAX_TIMEOUT` with a warning). A wait that times out returns `operation.timed_out: true` and the id to follow up with: a DockHand job id (`dockhand_get_job`) or this server's `op_id` (`dockhand_get_operation`, same principal only, kept 1 h, lost on restart).
- **Async**, as found: `job` = DockHand returns `{jobId}` (requested with `Accept: application/json, text/event-stream`; without `text/event-stream` DockHand would block), polled via `GET /api/jobs/{id}`, whose terminal status live is `done` (success or failure in `result`). `sse` = the spec describes an event stream; live DockHand 1.0.46 answered the two exercised ones (deploy, restart) with `{jobId}` instead, whose `lines` are the stream's events (`progress`, then `result`); both shapes are handled, the consumption runs in the operation registry, and every such tool also declares `GET /api/jobs/{id}`. `detached` = a synchronous endpoint run in the operation registry, so `wait=false` and timeouts still yield an `op_id`.
- Writes that persist content (`update_stack_compose`, `update_stack_env_raw`, `modify_stack_env`, `create_stack`) run the compose guardrails (SECURITY §5, with the stack's real variables) and, for compose, DockHand's validator first; results carry `data.guardrails` (`mode`, `blocked`, `counts`, `findings`, and `dockhand` for the validator). Then they **read the content back** and compare byte for byte: a mismatch is `ok: false, verified: false`, `error.code = "verification_failed"` (S3b; S3a answered `dockhand_http_error`), with `data.read_back` (line and byte counts, first 3 differing line numbers; never content). A write DockHand answers with a 5xx, or whose connection drops after the request was sent, is read back once too (#17): the content as sent → `operation_failed`, `verified: true`, `data.saved: true` ("DockHand reported an error, but the content was saved."); not saved (for `create_stack`: no stack) → `dockhand_http_error`, `saved: false`; the read-back failing (or, for `create_stack`, a stack with other content) → `dockhand_http_error`, `saved: "unknown"`, with a message to check before retrying. DockHand's status and body stay in `error`. With `redeploy`/`start`, `data.steps` gains a `read_back` step and a step's `outcome` may be `unknown`. A 4xx, and a connection never made, are unchanged.
- **Stack scope (S3g, #16):** every write to an existing stack first reads `GET /api/stacks?env` and goes ahead only when the stack is tracked there (`sourceType` set). This covers `start`/`stop`/`restart`/`deploy`, the compose and `.env` writes, and, in the destructive tier, `down` and `delete` in their previews. A stack that is only discovered there (no source record: on a Docker daemon shared by two environments, it can be the other environment's stack), or is not listed at all, is `not_found`, and no write request is sent. `dockhand_create_stack` creates a new stack and does not check.
- **Placeholder write-back guard:** content containing `<redacted>` or `***` (compose, raw `.env`, `set_vars` values, rename targets, `env_vars` values) is refused (`guardrail_blocked`) before any request.
- After every `.env` write `warnings` carries: "Running containers keep their old environment until the stack is recreated (dockhand_restart_stack mode=recreate or dockhand_deploy_stack force_recreate=true)".
- Output passes the same key-based secret redaction and free-text pass as the read tier. DockHand's answer to every write, and every error body, passes the full operation-output redaction inside the client (below), so detached results kept for `dockhand_get_operation` are stored redacted (S3e).
- **Operation output** (job lines, SSE progress entries, a job's or stream's final `result`/`error`, batch per-item messages) is redacted on one path inside the client modules (`client/redaction.py`, S3d): the key-based pass on structured lines; on every string, `logging.redact()`'s patterns (URL credentials, `scheme://user:pass@host` → `scheme://<redacted>@host`; `dh_…`, `Authorization`/`Bearer …`, `token=`/`password=` pairs, the configured secrets); then the 512-character cap on lines. The stack lifecycle tools (`start`/`stop`/`restart`/`deploy`, and `down` and `delete` in the destructive tier) first read the stack's variables (`GET …/env/raw`, `GET …/env`) and also mask any of their values of 8 or more characters (not DockHand's `***` mask); if the variables cannot be read the operation is not started. The compose and `.env` writes mask the variables they already read for the guardrails, plus a `.env` write's new values; `dockhand_create_stack` masks its `env_vars` values (S3e).
- **Failure codes:** an operation DockHand accepted and then reported as failed (a job ending `failed`/`cancelled`/`error`, a result of `success: false`, an SSE `error` event, any failed batch item, the start or redeploy half of a compound stack write whose save read back verified — S3f, a content write answered with a 5xx whose content reads back saved, and a pull whose scan after it failed — #17) is `operation_failed` (S3d; before, `dockhand_http_error`). `dockhand_http_error` stays for HTTP-level failures: a 4xx/5xx (a content write's only when the read-back does not show it saved), or an answer that can't be read (a malformed batch summary, a stream that ends without a result).

## Destructive tier (profile = admin, human approval per D-006) — Phase 3b

Implemented in S3b: 10 tools, each `Tier.DESTRUCTIVE` with its exact `(method, path)` declarations, registered only with `DOCKHAND_MCP_PROFILE=admin`. **Status** and **Perm** as in the operator tier; "live" means exercised in the test environment during S3b, on resources the session created.

Destructive-tier conventions (S3b):
- **Approval** (`auth/approval.py`, ARCHITECTURE §7). Every call runs through `run_destructive`: the per-principal rate limit (`DOCKHAND_MCP_DESTRUCTIVE_PER_MIN`; every destructive `tools/call` counts, the approval round included; over the limit → `not_available`), then the preview, during which the DockHand client refuses anything but a GET, then the approval decision, and only then the write.
  - *Elicitation* (MCP 2026-07-28, the request declares form elicitation, `DOCKHAND_MCP_CONFIRM_MODE` `auto` or `elicitation`): the first call answers `input_required` with one form (`dockhand_approval`) showing the preview summary and asking only `approve` (plus `scope_all_acknowledged` for `dockhand_prune scope=all`), and a signed, single-use, 120 s challenge as `requestState`. The client's retry with the human's answer runs the write. `confirm` is ignored. Declined or cancelled → `confirmation_required`, nothing done. A forged, expired, replayed or mismatched challenge (other principal, tool, arguments, or a name that now resolves to something else) gets a new question, never a write.
  - *Confirm path* (`param` mode, or `auto` when the request does not declare form elicitation, which includes every 2025-11-25 request): without `confirm=true` the result is `ok: false`, `error.code = "confirmation_required"`, `data.preview` = the dry run. With `confirm=true` the write runs.
  - `elicitation` mode and a request without the capability → `confirmation_required` with a message naming the mode; `confirm` does not help.
- Refusals that need no human (a running container without `force`, a network with attached containers, an unknown stack) happen in the preview, before anyone is asked: `guardrail_blocked` or `not_found`.
- Every approved result's `data.approval.method` is `elicitation` or `param`; every call logs one WARN `destructive_call` audit line per round (tool, principal, approval method, challenge nonce — never the challenge or its MAC —, preview counts, outcome).
- The write acts on the IDs the preview resolved. Sync endpoints run as detached operations (`wait=false` and timeouts give an `op_id`); job endpoints are polled as in the operator tier.
- Output passes the key-based secret redaction and the free-text pass; DockHand's answers, operation output and failure codes follow the operator-tier conventions (`operation_failed` for a failure DockHand reported, including a synchronous answer of `success: false`).

## Name resolution contract (`guardrails/names.py`)

```
resolve_container(env, ref) -> ContainerRef(id, name)
  ref matches ^[0-9a-f]{12,64}$  → treat as ID; verify by prefix match against list; if 0 matches → not_found
  else                           → exact name match (case-sensitive) against list; 0 → not_found; >1 → ambiguous_name (list candidates)
```
Same shape for networks (`resolve_network`) and images (`resolve_image`: ID — hex prefix or `sha256:…` —, exact `repo:tag` from `RepoTags`, or `repo@digest` from `RepoDigests`; a bare `repo` is not read as `repo:latest`, it is `not_found` with that repo's tags as candidates).

Implemented in S2. Also:
- A container or network ref starting with `/` is a `validation_error` ("names are given without Docker's leading '/'"). DockHand's lists carry names without it, while Docker's inspect `Name` has it; refs are never normalised (maintainer decision, 2026-09-24).
- Refs are validated before any call: no whitespace, control characters or `..`; Docker's name characters only.
- DockHand's list endpoints answer with lowercase keys (`id`, `name`, `repoTags`) where the spec documents Docker's (`Id`, `Name`, `RepoTags`); resolution reads both.
- `not_found` lists up to 10 similar names (case-insensitive substring); `ambiguous_name` lists every match as `name (12-char id)`.
