### 2026-09-20 — Project inception and locked decisions D-001…D-012 (no PR; planning)
**Decision:** Build a new, generic, security-first DockHand MCP server in Python on the latest stable series (3.14; D-001) with a latest-everything dependency policy enforced in CI (D-013), using the official `mcp` SDK, authenticating to DockHand with a `dh_` API token only, exposing a profile-gated tool set (`read-only` default), with a permanent `excluded` tier for credential/identity/exec/filesystem endpoints. Tier assignment for all 375 operations in DockHand API v1.0.46 is recorded in `docs/api/ENDPOINT-MAP.md` and generated by `scripts/gen-endpoint-map.py` (the `/api/docs` JSON itself is not committed).
**Why:** The reference implementation (`strausmann/mcp-dockhand`) stores a DockHand username/password in env, has no auth on its own MCP endpoint, and maps endpoints 1:1 including credential and exec endpoints. The maintainer's earlier private implementation proved the async patterns and read-back verification but is homelab-specific. A clean, publishable design was needed.
**Alternatives rejected:** TypeScript (viable; rejected for maintainer velocity — see ARCHITECTURE §1.1). Username/password login with auto-relogin (credential anti-pattern; DockHand tokens are the supported machine-auth path). 1:1 endpoint mapping (blast radius). Client-side profile selection (a compromised client could elevate).
**Deferred / follow-ups:** OAuth 2.1 resource-server mode for Claude.ai (Phase 5 scoping). Multi-token principals. Backups tier. `admin` tier. Container create with bind deny-list. Public launch checklist (license, SECURITY.md, CODEOWNERS).

### 2026-09-24 — Pre-implementation review (no PR; planning)
**Decision:** (1) Target MCP revision `2026-07-28` (D-014): stateless core, Multi Round-Trip elicitation, protocol headers. (2) Destructive confirmation moves from a model-settable `confirm` flag to human elicitation with an HMAC-signed, single-use, argument-bound challenge, keeping `confirm` as a configurable fallback (D-006, `DOCKHAND_MCP_CONFIRM_MODE`). (3) MCP feature surface fixed in ARCHITECTURE §7: tools + outputSchema + elicitation (+ progress/cancellation if the SDK supports them); resources, prompts, sampling, completions, logging notifications refused. (4) Per-principal destructive rate limit (S-11) and header/body integrity (S-12). (5) Distroless dropped from S-08: distro Python lags the latest CPython series and would violate D-013. (6) Endpoint-map fixes: `POST /api/stacks/{name}/validate` and `/env/validate` → `read`; `POST /api/git/stacks/{id}/deploy-stream` → `operator`; `POST /api/batch` → new `split` tier. (7) `main` stays the default branch (D-010). (8) Missing config variables added to ARCHITECTURE §5.
**Why:** The planning docs pre-dated the 2026-07-28 spec, which made sessions obsolete and gave elicitation a stateless shape. A model-settable flag doesn't stop a prompt-injected model. The endpoint-map mismatches would have made S2 and S3a hit their own STOP conditions.
**Alternatives rejected:** Stateful sessions (removed from the spec). Resources/prompts for convenience (injection amplification, no new capability). Strict `elicitation` as the default (would disable destructive tools on clients still rolling out 2026-07-28 support; recommended once supported).
**Deferred / follow-ups:** Tasks extension (plan §6). Completions.

### 2026-09-24 — CI right-sized for a private repo on GitHub Pro (no PR; planning)
**Decision:** Replace the multi-job CI (pip-audit, Trivy, Grype, CodeQL/Semgrep as separate jobs, push + PR triggers, daily Dependabot) with: one required `ci` job on PRs only, with docs-only fast pass and path-conditional Semgrep and Docker build; **OSV-Scanner** as the single vulnerability scanner (lockfile at every PR, image gate at release, weekly scheduled scan of the published image); Dependabot weekly grouped (security updates still immediate); CodeQL and secret scanning deferred to public launch. D-013 and S-09 amended.
**Why:** GitHub Pro includes 3,000 Actions minutes/month for private repos, billed per job rounded up; the original design (~8 jobs × multiple triggers × daily Dependabot) would have exceeded it. On Free/Pro, code scanning (CodeQL) and secret scanning only work on public repositories, so CodeQL couldn't run anyway. OSV-Scanner covers both `uv.lock` and the image's Debian/Python packages from the open OSV.dev database, needs no scanner DB download, and supports expiring exceptions (`ignoreUntil`). A weekly scan of the published image catches CVEs disclosed after release, which a build-time gate cannot.
**Alternatives rejected:** Trivy (more mature container scanning and Dockerfile misconfig checks; kept as the fallback if OSV-Scanner's image scanning proves insufficient), Trivy + Grype (minutes, duplicate coverage), third-party SaaS monitors such as Aikido or Snyk (an extra account and code access; maintainer declined), a self-hosted runner (runs workflow code on the maintainer's LAN; unsafe once the repo is public), scanning only locally (not enforced).
**Deferred / follow-ups:** CodeQL + secret scanning at public launch; revisit Dependabot cadence then.

**Verified at the source (spec 1.0.46, SDK 2.2.0):**
- *DockHand auth:* `bearerAuth` is evaluated on `/api/*` only when no session cookie is present, and 10 failures per IP give 429 for 5 minutes. A 401 means "not authenticated". A 403 means a missing permission, no access to the environment, or "Enterprise license required". It never means a wrong token. The client's two hints say exactly that, and neither status is retried.
- *Edition probe:* `GET /api/roles` is "available in setup mode or with an enterprise license", and its only 403 is "Enterprise license required". So 403 means Free. 200 means Enterprise only when `authEnabled` is true. With auth disabled, a 200 could be "setup mode", which the spec doesn't define, so it reports `unknown`. The body is never read (a streamed response, closed unread). `GET /api/auth/settings` is `security: []`, yet it documents 401 ("auth is enabled and the caller is not authenticated") and 403. Both are therefore read as "auth enabled".
- *Job statuses:* `GET /api/jobs/{id}` returns `{id, status, lines[], result?}`, and the spec enumerates no statuses. Terminal: `completed`, `failed`, `cancelled` and `error`. `running`, `pending` and `queued` are expected non-terminal values. Anything else is logged once as `unknown_job_status` (at most 100 remembered) and treated as running. **None were seen live:** the checks were read-only and created no job.
- *SSE event names:* taken from the 200 descriptions of the tool-reachable streaming endpoints (backup run/verify/restore, check-updates, stack deploy/restart, image pull/scan, image prune, scan-all, git deploy). They emit `progress` events and a final `result` event. `error` is treated as terminal too. Other events are kept as progress. The excluded raw feeds use `connected`, `heartbeat`, `log`, `stat` and `done`, which don't matter here. No stream was consumed live.
- *`Accept` and job endpoints (for S3a):* the stack `start`/`stop`/`down` descriptions say `Accept: application/json` "without text/event-stream" blocks and returns the final result synchronously. The client's default `Accept` is `application/json`, so S3a job tools must pass `accept=` explicitly to get a `{jobId}`. They should verify which value DockHand needs.
- *Protocol checks (S-12), SDK versus us:* the SDK routes on `MCP-Protocol-Version`. Its modern entry (2026-07-28 and any unknown value) already rejects the following with 400:
  - an unsupported version (`-32022`);
  - a version header that disagrees with `_meta`;
  - a missing or mismatched `Mcp-Method`;
  - a missing or mismatched `Mcp-Name` for `tools/call`, `prompts/get` and `resources/read`;
  - duplicated routing headers.

  Its legacy transport (no version header, or 2024-11-05 … 2025-11-25) checks none of these. `transport/protocol.py` covers that path: `Mcp-Method`/`Mcp-Name`, when present, must match the body; `Mcp-Name` on a method that carries no name is a mismatch; duplicates are rejected. The answer is a 400 with a JSON-RPC `HEADER_MISMATCH` error, the SDK's own shape. Tests cover both paths.
- *Tools-only capability surface:* the low-level `Server.get_capabilities()` derives capabilities from registered handlers. `MCPServer` always registers resources, prompts and `subscriptions/listen`. On 2026-07-28 the last one also turns `tools.listChanged` true. The server is therefore the public low-level `mcp.server.Server` with only `on_list_tools` and `on_call_tool`. One override remains. `Server.create_initialization_options()` always adds `experimental: {}` to the 2025-11-25 `initialize` result, so `ToolsOnlyServer` overrides that public method to drop the empty object. Nothing is patched. Both revisions advertise exactly `{"tools":{"listChanged":false}}`: tested over both, and seen live.
- *Progress and cancellation:* both work on both revisions. `ctx.session.report_progress()` emits `notifications/progress` when the request carried a progress token. On 2026-07-28 that commits the response to SSE, and it's a no-op otherwise. Cancellation reaches the handler as task cancellation: the client closing the stream on 2026-07-28, `notifications/cancelled` on the legacy path. Tools get `ctx.progress(message)`. The poller, SSE consumer and registry send our own text only (phase, elapsed seconds, and the job id or `op_id` when it is a safe identifier), at most one SSE progress report per second. A cancelled call stops waiting, is audited as `cancelled`, and never touches DockHand. A detached operation runs in the registry's task group and survives the cancellation. After a cancellation there is no response to carry the id, which is why progress messages include it. Tested end to end with a test-only tool.
- *2025-11-25 compatibility:* served by the SDK's stateless legacy transport. Tools, auth, capabilities and progress are tested over it, and a live run used both `auto` and `legacy` clients over HTTP and stdio. We don't narrow the SDK's handshake-era version set.

**Choices made within the prompt:**
- *Auth failures:* 10 failures in a sliding 5-minute window block the IP for 5 minutes. This follows SECURITY §2 and ARCHITECTURE §3; S-03's "10/min" is the laxer reading.
  - Only a wrong or malformed `Authorization` value counts as a failure. A missing header is not a guess.
  - A blocked IP gets 429 even with the right token.
  - The token is compared as the raw bytes after a case-insensitive `Bearer `, with nothing normalised (a trailing space is a different token). There is no early exit, over every configured token.
- *Principal:* the auth stage attaches it to `request.state`, and tools read it from there. `none` mode (loopback, explicit opt-in) uses `local`. stdio uses `stdio` and now requires `DOCKHAND_MCP_AUTH_MODE=none`, since stdio has no header to carry a bearer token. A missing principal on HTTP fails closed.
- *Client IP:* the socket peer. With `TRUST_PROXY`, the right-most `X-Forwarded-For` entry across all header lines, if it parses as an IP; otherwise the peer. Every limiter table is LRU-bounded at 10 000 keys.
- *Pipeline:* the body cap uses the SDK's `RequestBodyLimitMiddleware`, and Host/Origin uses the SDK's `TransportSecurityMiddleware`, run before auth. Both still run again inside the SDK.
- *DockHand client:*
  - `trust_env=False`: environment proxies, netrc and `SSL_CERT_*` are ignored, so traffic goes only to `DOCKHAND_URL`.
  - Timeouts: connect 10 s, read 30 s by default; tools pass `read_timeout`.
  - Retries: GET only, on unreachable/5xx, 3 attempts, backoff `0.5 s × 2^(n-1) × U(0.5, 1.5)`. Read timeouts, 4xx and non-GET methods are never retried.
  - Path parameters are percent-encoded with `safe=""`.
  - `allow_status` lets a caller accept a documented non-2xx body, as the database health 503 needs.
  - Unless a tool declared the endpoint at registration, the client refuses the call (`UndeclaredEndpointError`) before sending anything. This adds runtime enforcement to the endpoint-map test.
  - httpx/httpcore loggers are held at WARNING. The live run showed httpx logging every full URL at INFO, query values included.
- *Envelope:* this is Phase 1, where the envelope is defined.
  - `error` gains the optional `retry_after` and `detail` (the DockHand body, 2 KiB, redacted) fields.
  - The closed code set gains `unexpected_redirect`, which the prompt requires.
  - The text content is compact JSON, or `{"ok":…,"note":"truncated, see structured content"}` above 32 KiB.
  - Unknown tools, including tools outside the profile, give a JSON-RPC `-32602`, as the MCP spec says. Unexpected exceptions become a generic `-32603`, logged with the type only. Everything else is a tool error.
- *`dockhand_health`:* passes through only the spec's documented database fields; connection details are dropped. An unhealthy database (503) is `healthy: false`, not an error.
- *`dockhand_get_operation`:* sets `openWorldHint: false`, since it is in-process (TOOLS.md notes the exception). Its `op_id` must be a lowercase uuid4.
- *Audit line:* logger `dockhand_mcp.audit`, message `tool_call`, with `tool`, `principal`, `arguments` (only the arguments the tool lists in `audit_args`), `outcome`, `duration_ms`, `dockhand_status` and a per-call `request_id`. The field is named `arguments` because `args` collides with `LogRecord.args`.
- *`redact()`:* with no explicit list it uses the configured secrets. It also covers `Authorization` values in header, JSON and `key=value` form (keeping the scheme) and `*token*=`/`*password*=` pairs. Pairs are masked before `dh_…`, so `dh_token=` keys are still caught.
- *`check`:*
  - DockHand calls: health, database health, auth settings, environments (when a token is set or auth is off), the roles probe, and one list per domain (containers, stacks, images, volumes, networks) in the default or first environment. The domain lists are best effort, reported rather than fatal.
  - Output: JSON with `dockhand` and `problems`, exit 1 on any problem. Warnings go to stderr.
- *`serve`:* runs the SECURITY §6 "no `DOCKHAND_TOKEN` but auth enabled" rule before starting. An unreachable DockHand with no token also fails closed. Because of this rule, CI's hardened-run smoke step now passes a fake `DOCKHAND_TOKEN` generated at runtime. The container flags are unchanged.
- *Smoke client:*
  - Tiers are derived from annotations; MCP carries no tier field.
  - The token comes only from `DOCKHAND_MCP_TOKEN_FILE`.
  - Payloads are printed only with `--show`, and redacted.
  - The exit code is 1 on a failed expectation and 2 when the server is unreachable.
- *Docs:*
  - ARCHITECTURE §5 gains the missing `DOCKHAND_ALLOW_HTTP` row, taken from `config.py`: default `false`; the boolean forms `config.py` accepts; `http://` fails startup unless it is true. That resolves S0's open item, and nothing else in §5 changed.
  - §6 lists the new error fields and code.
  - §2's jobs row now names `error` as terminal.

**Could not verify / follow-ups:**
- Live job statuses, SSE streams, a DockHand 429 and its `Retry-After` format (the spec documents no such header), and the Enterprise edition path. The live checks could not reach the Enterprise path, and read-only checks create no jobs or streams.
- *Detached operations:* one that raises something other than `DockhandError` (a bug) is recorded as `failed` with code `dockhand_http_error` and an "internal error" message, because the closed set has no internal-error code. `RegistryFullError` has no envelope mapping yet, since no S1 tool starts detached work. S3a should decide both.

- *Test fixtures:* DockHand bodies in the tests are invented from the spec's schemas; none were recorded.

**Maintainer decisions (asked during the session, 2026-09-25):**

- *Variables are resolved the way docker compose does, with real values.* For `dockhand_create_stack`, its `env_vars`. For writes to an existing stack, `GET …/env/raw` plus `GET …/env`, with the proposed change on top. Substitution follows the compose spec (unset → empty; `:-`, `-`, `:+`, `+`; `:?`/`?` unset → error; `$$`). **Verified at the source (spec 1.0.46, then live against DockHand 1.0.46 in the test environment):**
- *Job vs SSE vs sync, per the spec:*
  - job: stack `start`/`stop`, `POST /api/batch`;
  - SSE: stack `deploy`/`restart`, image `pull`/`scan`, `scan-all`, `check-updates`, git stack `/deploy`;
  - sync: everything else. That includes `batch-update` and the container lifecycle endpoints, which block until Docker finishes, and `PUT …/compose` with `restart`, which redeploys synchronously.
- *Job `Accept`* (S1 handoff): the spec says `Accept: application/json` *without* `text/event-stream` blocks for the final result. Job tools send `application/json, text/event-stream`, and live DockHand answered `{jobId}`. A JSON answer without a job id is taken as the final result.
- *Live job statuses* (S1 handoff): jobs end with status **`done`**, which S1's poller did not know (it waited out the budget, logging `unknown_job_status` once). `done` is now terminal; success or failure is in `result.success`. `lines` are `{event, data}` records. No failed job was seen live.
- *Live SSE* (S1 handoff): asked for `text/event-stream`, live DockHand answered `deploy` and `restart` with `application/json` `{jobId}`, not a stream (the spec's "job-response channel"). The job's `lines` are the stream's events: `progress` with `{status}` or `{type: "line", line}`, then `result` with `{success, output}`, which the job also carries as `result`. The client now passes a JSON answer to an SSE request through as one terminal event, and the SSE path polls a job id when it gets one. Every SSE tool therefore also declares `GET /api/jobs/{id}`. Real event streams are still handled; the mocked tests use them. Pull, scan, scan-all, check-updates and git deploy were not exercised live and are `experimental`.
- *`mode`*: `restart` (default), `ordered`, `recreate`; the spec says any other value is a plain restart, so only those three are accepted.
- *`POST /api/batch`*: `entityType` `containers` (the spec's example, the only value it gives) and items `{id, name}`. The operation is a `Literal` of start/stop/restart/pause/unpause, checked again in the handler, so `remove`, `down` or anything else never reaches DockHand.

**Guardrail decisions made in-session** (bypass closures of the §5 rules; SECURITY §5 lists them):

- *Content the guardrails cannot see* is an error (`external_content_unchecked`): `extends` with `file:`, top-level `include`, and `volumes_from: container:…`.

**How no destructive tool can execute without approval (by construction):**
- A destructive tool's execute step is reachable only from `DestructiveHandler._run`, after `approve_or_request` returned `Approved`.
- The execute function also takes that `Approved`, which only `auth/approval.py` can create (its constructor needs a module-private token).
- The dispatcher refuses to serve a destructive tool whose handler is anything else.
- During the preview, the DockHand client refuses anything but GETs.
- Tested through the public tool surface: unapproved calls to every tool send zero non-GET requests; a preview that tries a DELETE is refused before it is sent; an ungated or borrowed handler is refused at server build.

**Elicitation wire format, as implemented through the low-level `Server` (spec pages and SDK source, 2026-09-25):**
- *Returning the question:* `on_call_tool` may return `mcp_types.InputRequiredResult`, and the runner serialises it on 2026-07-28 (`resultType: "input_required"`). It holds:
  - `inputRequests`: one form-mode `elicitation/create` under the key `dockhand_approval`. Its message is our text plus the preview summary (DockHand names; control characters stripped; at most 4000 characters). Its schema is a flat `{approve: boolean}`, plus `scope_all_acknowledged: boolean` for a prune of everything. It never asks for anything secret, as the spec requires.
  - `requestState`: the challenge.
- *Reading the answer:* the retry's `inputResponses` and `requestState` arrive on `CallToolRequestParams.input_responses` (typed `ElicitResult`) and `.request_state`.
- *Challenge:* `base64url(json{nonce, principal, tool, args_sha256, exp}) "." base64url(HMAC-SHA256(key, <that text>))`, 120 s.
  - The hash covers the validated arguments (defaults filled, environment resolved) and the preview's resolved target IDs, so a name that resolves to something else on the retry is asked again.
  - The spec says `requestState` is attacker-controlled, needs integrity protection, and that single use must be enforced server-side; the MAC and the replay cache do both.
- *Refusals:* a forged, expired, replayed or mismatched challenge, or a missing or malformed answer, gets a fresh `input_required` (the spec's SHOULD), never an approval. `decline`, `cancel` or `approve: false` → `confirmation_required`, and the challenge is consumed.
- *What we did not use:* the SDK's opt-in `RequestStateBoundary` (AES-GCM sealing of `requestState`) is not installed. It would be a second, differently-keyed layer, and single use would still be ours to do. It is a candidate if `requestState` ever carries more than the challenge.
- *Capabilities:* no server capability was added; `test_capabilities.py` is unchanged and passes.

**How capabilities are detected:** `ctx.session.client_capabilities`, which the SDK builds per request from `_meta["io.modelcontextprotocol/clientCapabilities"]` on 2026-07-28. Form elicitation is `elicitation.form` present, or an empty `elicitation: {}` (the spec's backwards-compatible form).

**2025-11-25 behaviour:** handshake-era requests never elicit.
- MRTR does not exist in that revision; there, elicitation is a server→client `elicitation/create` request during the call.
- The SDK's stateless HTTP transport builds each request's connection with no client info and no capabilities, and sets `can_send_request=False`. It can neither see the handshake's elicitation capability nor send the request.
- So in `auto` they take the `confirm` path; in `elicitation` mode destructive calls are refused.
- The same `approve_or_request` serves both revisions: the mode matrix is decided in one place, from the `ClientView`.
- Over stdio the SDK could elicit synchronously (`session.elicit_form`). That is a second approval mechanism, not implemented (deferred, below).
- *Observed:* Claude Code CLI 2.1.156, through a throwaway stdio capture server outside the repo, negotiated 2025-11-25 and declared `elicitation: {}` and `roots`.

**Replay-cache bounds:**
- At most 4096 used nonces, each kept until its challenge's `exp`. Expired entries are purged when the cache is full.
- A cache full of live entries refuses (fails closed) rather than forgetting a nonce that could be replayed. With the rate limit capped at 1000 per minute, at most 2000 can be consumed in one lifetime.
- Residual risk: with a configured `DOCKHAND_MCP_CHALLENGE_KEY`, a restart within 120 s of an approval forgets its nonce. With the default per-process key, challenges do not survive a restart at all.

### 2026-09-26 — Fix #6: batch per-item failures (PR #8, branch fix/batch-item-failures)
**Decision:** `dockhand_batch_containers` is `ok: true` only when DockHand's batch summary shows every item succeeded. The result now carries `data.summary` `{total, succeeded, failed}` and `data.items`: each container's id and name (from our own resolution, not DockHand's text), its `outcome` (`succeeded` / `failed` / `unknown`), and DockHand's per-item message, passed through `redact()` and truncated to 512 characters. `ok: false` with `dockhand_http_error` in these cases:
- any failed item, including all of them;
- a job that ends `failed` / `cancelled` / `error`;
- a result that is missing, not `{type: "complete", summary}`, has counts that are not non-negative whole numbers, has counts that don't add up, or has a total that differs from the number of items sent;
- a summary claiming no failures that a per-item `error` line contradicts.

A job still running (`wait=false`, or the wait timed out) is unchanged: `ok: true` with the job id, which is no verdict.

**Observed live** (DockHand 1.0.46, test environment, two containers in a session-created `mcp-smoke-` stack; ids and names redacted here). - `{type: "complete", summary}`.

### 2026-09-26 — Operation-output redaction and `operation_failed` (PR #10, branch sec/redact-operation-output)
**Decision:** Job and SSE output now goes through one redaction path before it can reach any tool result, and an operation DockHand accepted but reported as failed gets its own error code, `operation_failed`. **Tools covered**, taken from the registry (every tool declaring `GET /api/jobs/{id}`; `test_operation_output.py` derives the same list and fails if a new one appears unclassified):
- job: `dockhand_start_stack`, `dockhand_stop_stack`, `dockhand_batch_containers`, `dockhand_down_stack`, `dockhand_batch_remove_containers`;

`dockhand_get_operation` returns the stored envelopes of these, which are built from redacted output.

**Redaction layers** (`client/redaction.py`, `OutputRedactor`). It is applied inside `client/jobs.py` (a polled job's `lines` and `result`, the synchronous answer, `redact_job` for `dockhand_get_job`), `client/sse.py` (each progress entry, the terminal payload) and `client/batch.py` (per-item messages). In order:
1. Structured values: S2's key-based pass (sensitive key → `<redacted>`; `null` and booleans left alone).
2. Every string value and plain-text line:
   - the call's context values, longest first → `<redacted>`;
   - URL userinfo: `scheme://user:pass@host`, `scheme://token@host` → `scheme://<redacted>@host`. The userinfo cannot cross `/`, `?`, `#` or whitespace, so `ops@example.test` and `https://host/a@b` are left alone;
   - `logging.redact()`: configured secrets, `token=`/`password=` pairs, `Authorization`, `Bearer …`, `dh_…`.
3. The existing 512-character cap on lines and progress entries, applied after redaction, so a secret at the cut can't survive as a fragment (tested). Result payloads keep `cap_json` (64 KiB).

A JSON SSE progress entry gets the structured pass too, and is re-serialised only if that changed it. A JSON answer's `jobId` is read before redaction (`SseResult.job_id`), so a context value can never alter the id that gets polled.

**Context-aware redaction:** `_stackguard.output_redactor` serves the stack lifecycle tools (`start`, `stop`, `restart`, `deploy`; `down` after approval).
- Before starting, it reads `GET …/env/raw` and `GET …/env`. Both are `read` endpoints, now declared by those five tools (catalogue `endpoints` changed deliberately).
- It masks every value of at least 8 characters: `.env` values as written and as interpolated, plus DockHand's stored variables.
- The values live only in that call's redactor and are never logged. Live, the three server logs contained the dummy value 0 times.
- **Fail closed:** if the variables can't be read, the operation is not started and DockHand's error is returned. S2's `redact_compose_env` set the precedent: output that can't be redacted is never produced. This adds a precondition; it does not change how a started operation's success or failure is judged.
- **Limits:** values under 8 characters (they would mask ordinary words); values DockHand masks as `***` (their real value is never seen); values not in the stack's env (DockHand's process environment, image defaults); `dockhand_get_job` (a bare job id has no stack context); `dockhand_deploy_git_stack` (no environment or stack name, and `GET /api/git/stacks/{id}` has no response schema to find them from). Those still get every pattern layer.

It carries the same per-item messages, now through the central path, and each is tied to our own resolved id and name. Restoring the tail would add about 3 KiB of duplicate JSON per call and no information. The full job stays readable through `dockhand_get_job`, which is now redacted too. `dockhand_batch_remove_containers` keeps the generic tail, as before.

### 2026-09-26 — Output redaction for direct answers; URL credentials in logs; SECURITY.md (PR #12, branch sec/redact-direct-answers)
**Decision:** Every DockHand answer a tool can return now passes S3d's `OutputRedactor`, with the same layer order. `logging.redact()` gains the URL-credential rule, and that rule now has one implementation. SECURITY.md gains an "Output redaction" subsection. Fixes #11, which files S3d's three follow-ups.

**Where it is enforced:**
- *Direct answers (`client/dockhand.py`):* every answer to a non-GET request (`post_json`, `put_json`, `delete_json`) passes the call's redactor, all layers, before the caller sees it. A top-level `jobId` is kept as sent, since it is what gets polled (S3d's rule for SSE).
  - A detached operation builds its result from these answers, so what the registry stores, and `dockhand_get_operation` returns, is already redacted.
  - The redactor is call-scoped: `redacting()` binds it in a `ContextVar` (default `PLAIN`), and detached tasks inherit it, as they already inherit the declared-endpoint check. `run_async_pattern` binds the redactor it is given, or the one already bound, for the whole operation.
- *Error bodies (`client/errors.py`, called by the client):* `error.detail` gets all layers with the call's redactor: JSON gets the structured pass, then the string layers, all before the 2 KiB cut. Before, it got `redact()` only.
- *Free text in every result (`server.py`):* after S2's key pass, the dispatcher applies the string layers, without context values, to values under free-text keys: `message`, `messages`, `msg`, `error(s)`, `status`, `output`, `stdout`, `stderr`, `reason`, `detail(s)`, `warning(s)`, `hint`, case-insensitive, whole names or suffixes (`errorMessage`, `State.Error`, a health check's `Output`, a container's `status`).
  - The key list was chosen from the spec's property names and Docker's inspect fields.
  - Content a tool exists to return (logs, compose, `.env`, stack variables, `Config.Env` under `redact_env`, generated compose) sits under other keys and is unchanged.
  - Names are never under these keys, so a name shaped like a `dh_` token is not mangled (tested).

**Why GET answers are redacted at the dispatcher, not in the client:** the prompt asked for the client layer. For write answers that is what was done. GET bodies, though, feed decisions: name resolution (a container named `dh_…` would stop resolving), guardrail interpolation, byte-for-byte read-back, and job status (a context value could rewrite a status). Redacting them in the client would change what tools consider success or failure, which is a STOP condition. The dispatcher is the other place no tool can skip. It runs after every decision is made and redacts only what leaves the server.

### 2026-09-26 — create_stack name-collision guard (PR #20, branch fix/create-stack-name-collision)
**Decision:** `dockhand_create_stack` refuses a name already in use as a compose project on the environment's Docker daemon. Before any other request (DockHand's validator included), it reads `GET /api/stacks?env` and refuses with `validation_error` when any listed item, tracked or only discovered, has the same name after Docker Compose's project-name normalisation. The message says the name is in use on this Docker daemon, names the matching project, and says whether it is tracked in this environment. No write request is sent. Fixes #19, which files S3g's follow-up.

**DockHand's observed behaviour** (1.0.46; environments A and B on one daemon, B being the test environment; `mcp-smoke-` stacks only; before the fix, through a raw client):
- A stack created and started in environment B was listed in environment A with no `sourceType`, as S3g saw.
- A create through environment A with the same name and `start=false` was **accepted** (`success: true`). Environment A then listed it as **tracked** (`sourceType: internal`, status `running`: the other environment's containers), with its own compose file (a different path). Environment B's compose file and container were unchanged at that point.
- Deleting that duplicate through environment A (`force=false`, `volumes=false`) answered `success: true` and ran `compose down` on the shared project: **environment B's container was removed**, and its record stayed, as `created`.
- So DockHand does not refuse; the guard is the control, not only defence in depth. A duplicate that exists is also tracked in both environments, so S3g's tracked-stack check cannot tell them apart. `start=true` on a duplicate was not attempted.

**Image gate policy** (maintainer decision, 2026-09-26, after this session's STOP).

The first local scan (OSV-Scanner v2.6.0, both platforms) reported **65 vulnerability IDs in 17 Debian trixie source packages**:

### 2026-09-26 — Fix #17: 5xx after save; scan after pull (PR #25, branch fix/issue-17)
**Decision:** The two questions S3f left open, deferred to after v0.1.0 as #17, are fixed for v0.1.1.
- A content write that DockHand answers with a 5xx, or whose connection drops after the request was sent, is read back once. The result says whether the content was saved.
- `dockhand_pull_image` with `scan_after_pull` reads the scan's outcome from the pull's own events. A pull whose scan failed is never a success.

No new error code, no schema change: the three catalogue snapshots and every tool description are unchanged. Each write's read-back endpoint was already declared.

**(1) 5xx after a save.** Tools: `dockhand_update_stack_compose`, `dockhand_update_stack_env_raw`, `dockhand_modify_stack_env`, `dockhand_create_stack`. `test_saved_after_error.py` derives the list from the registry (every tool declaring `PUT …/compose`, `PUT …/env/raw` or `POST /api/stacks`) and fails on a new one.
- *What triggers the read-back* (`_common.may_have_written`):
  - a 5xx;
  - a transport failure after the request went out (a dropped connection, a read timeout). `DockhandError` gains `sent`: always true with a status, and false for `ConnectError`, `ConnectTimeout` and `PoolTimeout`, which never reached DockHand.
  - Error codes are unchanged; only the flag is new.
  - Not triggered: a 4xx (DockHand refused), a connection never made, and every 2xx path. Those are unchanged. Non-GETs are still never retried.
- *Outcomes* (`check_saved`, `write_error`):
  - **Saved**: the content reads back byte-equal to what was sent. `ok: false`, `operation_failed`, `verified: true`, `data.saved: true`. The message starts "DockHand reported an error, but the content was saved." and says what to do instead of writing again (redeploy, deploy, or nothing).
  - **Not saved**: `dockhand_http_error`, `saved: false`. For an update, the stored content differs from what was sent (the previous file, or anything else: this call's content is not there, and `data.read_back` has the count-only diff). For a create, `GET …/compose` answers 404: no stack.
  - **Unknown**: `dockhand_http_error`, `saved: "unknown"`, and the message ends "Read it before retrying." This covers a failed read-back, and, for a create only, a stack that now exists with other content. The collision guard found the name unused, so that stack is not known to be this call's.
  - Every outcome keeps DockHand's `dockhand_status`, `retry_after` and redacted `detail`.
  - `verified` is `true` only when saved. After a create that was saved, the variables are checked as after a successful create: a mismatch gives `verified: false` with `data.read_back`; a failed variables read keeps `saved: true`, with `verified: null` and a warning.
  - A saved `.env` write keeps the recreate reminder.
- *Compound writes* keep S3f's `data.steps` and add a third step, `read_back` (`succeeded`, or `failed` with our read error's message):
  - `save`/`create`: `succeeded` (with `verified: true`), `failed`, or `unknown`. `step()` now takes `None` for `unknown`.
  - `redeploy`/`start`: `failed` when the read-back shows saved or not saved. DockHand saves before it deploys, so an unsaved file was never deployed. `unknown` when the read-back failed.
  - `data.redeployed` / `data.started` are `false`; `data.saved` / `data.created` carry the outcome.
- *Why "not saved" for any other content on an update:* the model's next step is the same (write again), and the previous file is not fetched, so no request is added to the successful path. A partly written file also lands here, which is the case where writing again is right.
- *Tests-only:* a real DockHand 5xx after a save cannot be provoked safely, so this was not exercised live.

**(2) Scan after a pull.**
- *The spec* says only "stream pull (and optional scan-on-pull) progress", "ending with a result event". The failure shape is not in it.
- *DockHand's source* (github.com/Finsys/dockhand, tag v1.0.46; read only, nothing copied):
  - `src/routes/api/images/pull/+server.ts`, `handleScanOnPull`. When the scan throws, it sends a `progress` event `{status: "scan-error", error}` and then, as on success, `result {status: "complete"}`.
  - `src/lib/server/scanner.ts`, `scanImage`. With scanner `both`, one scanner failing while the other completes does not throw: the only trace is that scanner's `scan-progress` event with `stage: "error"` ("Trivy scan failed: …"), and `scan-complete` then lists one result.
  - `src/lib/server/sse.ts` / `jobs.ts`. A thrown pull error fails the job (`status: error`, `result {success: false}`), which was already `operation_failed`. Pull failure is unchanged.
- *Live, successful shape* (the test environment, `busybox:1.36.1`, a tag not on the daemon; scanner setting `both`, both scanner images already present):
  - The answer was `{jobId}`. The job ended `done` with `result {status: complete}`: no `success` field.
  - 79 lines: the pull's progress, `complete`, `scanning`, 66 `scan-progress` (stages `checking`, `scanning`, `parsing`, `complete`; each scanner's `complete` carries its result), `scan-complete` (with `results`), then `result`.
  - Before this fix the tool said `ok: true` for this. After it, the same live pull says `ok: true`, with the same data keys and no warning.
- *Scan failure, live:* **not observed**. Every way to provoke it (a scanner image that isn't there, another scanner, bad scanner arguments) changes DockHand's scanner settings or other images, which the prompt rules out. It is covered by tests. Its fixtures (`jobs/pull-scan-error`, `jobs/pull-scanner-error`) are invented from the source and say so. `jobs/pull-scan-done` is the live recording, trimmed and sanitised.
- *How the tool reads it:*
  - `consume()` gains `on_event`, and `poll_job()` gains `on_line`. They see every event, or every line of the finished job, redacted and not capped. The returned `progress` tail (20 lines) and a job's `lines` (the first 500) would not reliably hold the scan's events at the end of a long pull.
  - `run_sse` gains `review`, which judges the finished envelope inside the operation, so `dockhand_get_operation` returns the same verdict after `wait=false` or a timeout. A timed-out or failed envelope is passed through.
  - `images.ScanWatch`: a `scan-error` event, or a `scan-progress` event with `stage: error`, gives `ok: false`, `operation_failed`, `data.pulled: true`, `data.scanned: false`, and `data.steps` (`pull` succeeded; `scan` failed, with the messages: at most 5 distinct, joined, redacted, capped at 512 characters). The rest of `data` (`job_id`, `result`, `progress`) is kept.
  - One scanner of two failing counts as a failed scan. The configured scan did not complete, and saying `ok: true` would hide it.
  - No scan at all (scanner `none`, which DockHand skips silently) stays `ok: true`, with a warning that the image was not scanned.
  - Without `scan_after_pull`, scan events are not judged.
- *Image hygiene, both live pulls:* the image list was recorded first. `busybox:1.36.1` was absent, its image id too, and no container used it. After each pull, exactly that one image was new. It was removed by id through `dockhand_remove_image` (admin, `CONFIRM_MODE=param`, preview first), and the list matched the recorded one. No prune.

### 2026-09-26 — Scoping: OAuth resource-server mode (PR #26, branch docs/scoping-oauth)
**Decision:** Phase 5 scoping only; no code or configuration changed. `docs/handoff/oauth-resource-server.md` holds the full design, evidence and test plan. Every claim in it carries a source fetched on 2026-09-26, marked verified or unverified. Recommendation:
- **Implement `oauth` mode now, as our own middleware** in the auth slot of the ARCHITECTURE §3 pipeline, beside `BearerAuthMiddleware`.
- **Validate JWT access tokens with PyJWT** (already in `uv.lock` through `mcp`). Serve RFC 9728 metadata at the path-inserted well-known URI, using the SDK's `ProtectedResourceMetadata` model.
- **Never combine it with bearer mode** in one instance (SECURITY §3 stands).
- **Ship it as experimental**, recommending the `operator` profile for connector-facing instances.
- **Model and effort** for the implementation session: Opus 5.5, high.

**Why:**
- *The spec permits exactly this design.* MCP 2026-07-28 defines the MCP server as an OAuth 2.1 resource server and never requires it to host or proxy the authorization server. So SECURITY §3 holds, and neither STOP condition applied. Its new authorization changes are all client- or AS-side: RFC 9207 `iss` validation, the DCR deprecation in favour of CIMD, and the AS-metadata issuer check.
- *Claude's custom connectors* (claude.ai, Desktop's Connectors, mobile) discover the AS through a 401 carrying `resource_metadata`. They register by CIMD, DCR or a pre-registered public client. They send RFC 8707 `resource` and PKCE S256, and they call from Anthropic's egress range `160.79.104.0/21`.
- *Connectors don't elicit.* They follow the 2025-03-26 to 2025-11-25 authorization specs, and elicitation is an open request (`anthropics/claude-ai-mcp#153`). Over a connector, D-006 approval degrades to `confirm` plus Claude's per-tool "Needs approval".
- *Verified IdP support.* Pocket ID 2.16 binds `aud` from `resource` and issues RFC 9068 JWTs with stable features. Keycloak 26.7.4 works with an Audience mapper, or with experimental CIMD. Authelia and Authentik work only with a pre-registered client and a fixed audience. Zitadel cannot put our URL in `aud`.
- *SDK support.* The SDK's low-level `Server` does accept `auth`/`token_verifier`, but it has no JWT/JWKS verifier. Its `RequireAuthMiddleware` also omits `scope` from the 401, records no failures, and adds CORS `*` to its metadata route, so the middleware is ours.

**Alternatives rejected:**
- *A sidecar proxy* (oauth2-proxy or a small AS in front). The per-user principal bound into `op_id`s, approval challenges and the destructive rate limit would collapse to one static principal, and scope→profile mapping would be impossible.
- *Implementing later.* The open connector bugs (#228 refresh, #341 discovery) don't change the design.
- *The SDK's `BearerAuthBackend`/`RequireAuthMiddleware`* (reasons above).
- *Allowing bearer and oauth together:* a static token would become the weakest credential on an internet-facing endpoint, with two principal namespaces and ambiguous audit.
- *Introspection / opaque tokens in v1:* every recommended IdP can issue JWTs. Introspection adds a secret and puts the IdP on every request's path.

**Single biggest risk:** an IdP granting our audience too broadly. Examples: a Keycloak Audience mapper in a default scope, user self-signup, or open DCR plus consent phishing. The design therefore makes a subject (or verified email-domain) allow-list mandatory and offers a client allow-list.

**Versions:** `uv lock --upgrade` changed nothing (52 packages): `mcp` 2.2.0, `httpx` 0.28.1, `pydantic` 2.13.5, `pydantic-settings` 2.15.0, `pyyaml` 6.0.3, `starlette` 1.7.0, `uvicorn` 0.54.0, and, relevant here, `pyjwt` 2.15.0 and `cryptography` 50.0.1 (both via `mcp`). Dev: `ruff` 0.16.9, `mypy` 2.3.1, `pytest` 9.1.1, `pytest-asyncio` 1.4.0, `respx` 0.23.1. python.org's newest stable release is still 3.14.7, so there is no Python bump. No dependency was added.

**Deferred / follow-ups (the handoff's open questions, for the maintainer):**
1. Direct PyJWT dependency.
2. D-005 reading for per-request profile ceilings.
3. The proposed `DOCKHAND_MCP_RESOURCE_URL` / `DOCKHAND_MCP_OAUTH_*` schema, and whether to allow a fixed-audience override.
4. Scopes in the 401 challenge.
5. Whether `oauth` + `admin` must require `CONFIRM_MODE=elicitation`.

### 2026-09-27 — Fix #3: dockhand_list_tags (PR #7, branch feat/list-tags)
**Decision:** One read-tier tool, `dockhand_list_tags`, answers "what's tagged X?" and lets a client pick containers or stacks by tag before acting on them. It reads `GET /api/tags` (the global catalogue), `GET /api/container-tags?env` and `GET /api/stack-tags?env`, and returns in the uniform envelope:
- `tags`: the catalogue, `[{id, name, color}]`;
- `containers` and `stacks`: `{name: [tag names]}` for the environment, with untagged resources omitted;
- tag ids resolved to names through the catalogue; an id the catalogue lacks appears as `"#<id>"` and adds one warning listing the missing ids;
- a per-environment answer that is not a JSON object is shown as `{}` with a warning, never as silently empty.

`env` is always sent on both per-environment reads, although spec 1.0.49 marks it optional there (so the client's env guard from #5 does not enforce it). The tool is `Tier.READ` (registered in all three profiles), with `title`, `readOnlyHint: true`, a specialised `outputSchema`, and its output goes through the dispatcher's usual key-based and free-text redaction. Tags attach to workloads (containers, stacks) and help select them for an action; environment labels are cosmetic metadata on DockHand's own configuration. Future spec adoptions should classify similar metadata the same way: selection metadata on workloads is `read`, cosmetic metadata is `excluded`.
- *Declared endpoints:* the prompt said the tool declares "exactly its three GET endpoints", which conflicts with the read-tier convention (F-09) that every environment-scoped tool takes an optional `environment_id` and declares `GET /api/environments` to resolve it.
